# health

Одна команда: жива ли машина.

Показывает то, что иначе проверяется руками по десять минут —
сервисы, диск, свежесть бэкапов, карантин синка, кит, заслоны
Telegram, права на ключи, конфиг агентов.

```
health            коротко, без сети
health -v         подробно, плюс проверка порта сервера
health --no-color
```

Код возврата: `0` — всё хорошо, `1` — есть предупреждения, `2` — есть
поломки. Годится для проверки в скрипте.

```
$ health
    ОК    сервис tg-logbook      pid 3526, жив 7 мин
    ОК    бэкапы сессий          6 шт, свежий 2 мин назад (11.0 МБ)
    ОК    снимок читается        11 сессий в базе
    ОК    карантин md            пусто, всё уехало
   ВНИМ   ключ к серверу         права 0o644 — ssh отвергнет
  СТОП:  1 поломка, 1 предупреждение
```

## Системные сервисы

Отдельно проверяется всё, что лежит в `/var/service`: `openrgb`,
`udevd`, `elogind`, `greetd`, `dbus`, `agetty-*`.

Смотреть там нечем. Каталоги `supervise/` принадлежат root,
`sv status` отдаёт «access denied», и аптайм оттуда не достать.
Единственное, что доступно без прав, — `/proc`. Оттуда и берётся
всё: `/proc/PID/stat` читается даже для процессов root, поэтому
аптайм чужого процесса считается без всяких прав.

Три вещи, на которых ломается наивная проверка, и все три проверены
на живом runit:

**`runsv` жив даже когда сервис лежит.** Он его караулит и ждёт.
Судить только по нему — значит объявить мёртвое живым. Различает
наличие рабочего процесса, а не супервизора.

**`vlogger` от log-сервиса — тоже ребёнок `runsv`.** У сервиса с
логированием детей два, и лежащий сервис с живым log-сервисом
выглядит как работающий. `vlogger` в кандидаты не идёт.

**Ребёнок падающего сервиса мимолётен.** `run` умирает, `runsv`
перезапускает его через мгновение — можно поймать в `/proc` и
решить, что всё живо. Поэтому аптайм рабочего процесса участвует
в решении: поднявшийся меньше чем на полторы минуты даёт
предупреждение, а не «всё хорошо».

Отключается строкой в конфиге:

```
check_system = no
```

## Конфиг

Имена сервисов, путь к ключу и адрес сервера **не зашиты в код** — они
лежат в `~/.config/health/config`. Репозиторий публичный, а проверять
надо конкретную машину; конфиг — единственное место, где живёт
обстановка.

```
services = alpha, beta, gamma
ssh_key = ~/.ssh/id_ed25519
server_host = 192.0.2.1
server_port = 22
```

Без конфига скрипт работает, но ищет сервис по имени `my-service` и
ничего не найдёт — это видно сразу, молча он не проходит. Пустой
`services` не обнуляет список: проверка не должна выключаться сама.

Строка `ключ=значение`, `#` в конце — комментарий. Битый порт
игнорируется, а не роняет скрипт.

## Что проверяется

| Что | Как |
|---|---|
| сервисы runit | `sv status` плюс `supervise/pid` и `/proc` |
| падение по кругу | счётчик перезапусков в выводе `sv status` |
| подмена pid | имя сервиса ищется в самом процессе **и в его родителях** |
| диск | свободное место и заполнение, отдельно система и дома |
| бэкапы | свежесть последнего снимка, число, `integrity_check`, наличие сессий |
| карантин `md-unsent` | любой файл там означает, что синк его не увёз |
| кит | возраст `void-kit.7z` |
| Telegram | токен заполнен, права 600, `armed`, `PAUSE` |
| ключ к серверу | права на ключ из конфига |
| системные сервисы | `/var/service` целиком: есть ли рабочий процесс |
| конфиг opencode | модель по умолчанию, число агентов и навыков |

## Чего скрипт не делает

Ничего не чинит, ничего не отправляет, сеть по умолчанию не трогает.
Только читает. Проверка Telegram — по конфигу, без обращения к Bot API:
иначе `health` сам съедал бы лимит отправок, который сам же и сторожит.

## Почему проверка pid идёт вверх по родителям

Run-скрипт, который держит трап, не может делать `exec` — иначе
шелл заменится и трап пропадёт. Поэтому в `cmdline` остаётся
`/bin/sh ./run`, без имени сервиса. Имя живёт в родителе:
`runsv my-service`. Проверка только самого процесса давала ложное
срабатывание на сервисе, который держит трап в run-скрипте.

## Тесты

```
python3 tests/test_health.py
```

37 тестов. Проверяют не то, что скрипт запускается, а то, что он
ловит поломку: мёртвый сервис, удалённый каталог, файл в карантине,
битый и пустой снимок, протухшие бэкапы, права, пустой токен,
исчезнувший кит. Плюс контрольный случай — чистая машина обязана
проходить. Отдельно — системные сервисы на подставном `/proc`:
нет `runsv`, `runsv` без детей, только `vlogger`, только что
поднявшийся, аптайм не от `vlogger`.

Скрипт, который всегда говорит «всё живо», хуже отсутствия
скрипта.

install -Dm755 bin/health ~/.local/bin/health
